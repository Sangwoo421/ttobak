## 예상 Q&A (20초 답변)

| 질문 | 답 |
|---|---|
| 왜 STT 를 학습시키지 않았나? | 모델 학습은 범위 밖으로 뒀다. 대신 인식이 깨진 상태를 전제로, 화면에 있는 유한한 후보와 대조하는 레이어를 얹었다. 엔진이 바뀌어도 그대로 쓸 수 있다. |
| 오인식으로 엉뚱한 사람에게 보내면? | 보내지 않는다. 이체 API 가 없다. 수취인·금액은 자모 유사도 기준을 넘어야 하고, 넘어도 확인 톤으로 되묻고, 그 뒤에도 창구 요약서에 담길 뿐이다. |
| LLM 환각은? | LLM 은 규칙 엔진이 준 facts 만 받아 설명 문장을 만든다. facts 밖의 숫자·이름이 나오면 정해진 문장으로 대체한다. 판정 자체는 LLM 이 하지 않는다. |
| 개인정보·음성 데이터는? | 음성 원본은 저장하지 않는다. 텍스트와 판정 근거만 로그로 남긴다. 요약서 계좌번호는 마스킹된다. |
| KB스타뱅킹에 어떻게 붙나? | 거래내역 조회·본인 인증을 인터페이스로 분리했다(`TransactionProvider`, `AuthProvider`). 이 경계면만 실제 구현으로 교체한다. |
| 왜 앱 안에서 이체까지 안 하나? 은행 입장에선 앱 완결이 낫지 않나? | 이 사용자층은 기계를 믿지 못해서 창구에 온다. 1단계는 창구 연계로 신뢰를 쌓고, 판정 로그가 쌓이면 소액·등록 수취인 한정 실행을 검토할 수 있다. 단계적 확장이 설계 조건이다. |
| 창구 직원 부담이 늘지 않나? | 반대다. 받는 사람·금액이 여러 번 되물어 확정된 상태로 오므로 직원은 확인부터 시작한다. 요약서 제시 후 상담 시작까지 시간을 리허설에서 자체 측정했다(수치). |
| 비용은? | 세션당 STT·TTS·LLM 호출 수 건, 대사 캐시로 TTS 는 재사용. 규칙 우선이라 LLM 호출은 설명·동점 선택에만 쓴다. (건당 추정치 준비) |
| 측정은 믿을 만한가? | 자체 구성 테스트셋(N건, 팀원 녹음)이라고 명시했다. 같은 STT 엔진에 같은 파일을 넣었으므로 차이는 레이어에서만 난다. 규모는 작지만 방법은 재현 가능하다. |
| 일반 고객에게도 쓸 수 있나? | 쉬운 안내 수요는 전 연령에 있다. 어르신 모드는 말투·속도·되묻기 정책이 다를 뿐 구조는 같다. 3단계 로드맵. |
| 알림 뮤트는 누가 정하나? | 사용자. 시스템은 무엇을 읽을지 판정하지 않는다. 미청취·최근순 3건만 읽는다. |
| 사투리는? | 표준 발화를 전제하지 않는다. 후보 대조는 자모 단위라 발음 변이에 어느 정도 강건하고, 안 되면 버튼으로 넘긴다. 데이터 축적 후 엔진 튜닝은 다음 단계. |
| 동점 후보를 LLM 이 고르면 그것도 판정 아닌가? | 후보는 규칙이 좁힌 2~3개이고, LLM 선택 뒤에도 확인 톤 되묻기를 거친다. LLM 은 실행 게이트를 열지 못한다. |
| 실제 어르신 테스트는? | 본선 기간엔 팀원 가족 녹음으로 대체했다. 범위 밖으로 명시했고, 1단계 파일럿의 첫 과제다. |
| 왜 새 앱이 아니라 부가 모드인가? | 설치·가입·인증이 이 고객층의 가장 큰 장벽이다. 앱을 하나 더 깔게 하는 건 기획 전제와 맞지 않는다. |
