# 발표에서 할 말 — 설계 결정과 그 이유

지금까지 내린 결정들을 발표·질의응답에서 바로 쓸 수 있게 정리했다.
**여기 적힌 것은 전부 실제로 코드에 있고 실행해서 확인한 것이다.** 만들지 않은 것은 "안 만들었다"고 적었다.

---

## 1. 한 문장으로

> 어르신이 창구에서 하려던 일을 앱에서 미리 정리하고, 앱이 풀 수 없는 것은 그대로 창구 직원에게 넘기는 대화형 서비스.

세 가지 약속으로 나눠 말하면 이렇다.

| 약속 | 무슨 뜻인가 |
|---|---|
| **못 알아들어도 하려던 일에 도달한다** | 인식 정확도를 올리는 게 아니라, 깨진 상태에서도 목적지에 닿게 한다 |
| **모르면 지어내지 않고 창구로 넘긴다** | AI가 답을 못 하는 지점이 실패가 아니라 정상 경로다 |
| **AI에게 돈을 움직일 권한을 주지 않는다** | 이체 실행 API가 저장소에 아예 없다 |

---

## 2. 왜 이걸 만들었나 (배경)

**앱으로 다 되는 시대인데 어르신은 창구에 간다.** 이유는 대체로 세 가지다. 잘못 누를까 봐 겁이 난다. 어디를 눌러야 할지 모른다. 기계를 믿지 못한다.

앞의 둘은 앱을 쉽게 만들면 줄어들 여지가 있지만 **세 번째는 그렇지 않다.** 신뢰하지 않는 사람에게 더 좋은 기술을 주는 것으로는 풀리지 않는다.

그래서 이 프로젝트는 **어르신을 앱 안에 붙잡아두려 하지 않는다.** 앱이 할 수 있는 데까지 하고 나머지는 사람에게 넘긴다.

### 숫자

| | |
|---|---|
| 국내 18개 은행이 고령자모드 출시 완료 | 2023년 6월까지 |
| 고령자모드 이용자 중 40·50대 비중 | 45.2% (그래서 당국이 '간편모드'로 개명) |
| 모바일뱅킹 이용자 중 60대 이상 | **10.3%** |
| 은행 고객 중 60대 이상 비중 | **21.2%** |

**글씨를 키우고 메뉴를 줄이는 것으로는 고령층을 앱 안으로 데려오지 못했다.** 위의 세 가지 이유 중 어느 것도 화면 배치로 해결되지 않기 때문이다.

---

## 3. 기존 서비스와 무엇이 다른가

### 대화형 뱅킹은 이미 있다

신한은행 AI 음성뱅킹은 450여 개 업무를 지원하고, 케이뱅크는 음성으로 수취인을 찾는 AI 이체를 내놨다.

**다만 이들은 "○○에게 30만 원 보내줘" 같은 완성된 문장을 전제한다.** 어르신이 실제로 하는 말은 "아들이 뭐 보내라는데 이거 어떻게 하는 거야"에 가깝다.

| | 기존 음성 뱅킹 | 또박또박 |
|---|---|---|
| 전제하는 사용자 | 명확한 명령을 말할 수 있는 사람 | **무엇을 물어야 할지 모르는 사람** |
| 알림 | 눈으로 읽어야 하는 문자 | 눌러서 듣고 이어서 물어볼 수 있는 대화 |
| 인식 실패 시 | 다시 말하라고 요구 | 후보를 좁혀 되묻거나 버튼으로 전환 |
| 답을 못 하면 | 답변 실패 또는 추측 생성 | 확인 불가를 밝히고 창구로 연결 |
| 실행 권한 | AI가 이체까지 수행 | **돈이 움직이는 행위는 실행하지 않음** |

### KB미리작성서비스와도 다르다

KB에는 이미 모바일 번호표와 미리작성서비스가 있다. 심사위원이 알고 있을 수 있으니 미리 구분해 두는 게 좋다.

| | KB미리작성서비스 | 또박또박 |
|---|---|---|
| 언제 | 은행 도착 후, 번호표 뽑고 대기 중 | **집에서, 가기 전에** |
| 누가 | 양식을 읽고 쓸 수 있는 사람 | **무엇을 물어야 할지 모르는 사람** |
| 무엇을 | 정해진 신청서 빈칸 채우기 | 용건 자체를 찾아내기 |
| 모르는 항목 | 빈칸으로 남음 | **"창구에서 여쭤볼 목록"에 담김** |

같은 목적이지만 **양식을 못 읽는 사람은 미리작성서비스를 못 쓴다.**

## 4. 핵심 설계 ①: 음성 대응 레이어 3겹

모델을 새로 학습하지 않고 상용 STT 위에 세 겹을 얹었다.

### 입력 전 — 발화 종료 판정 대기시간을 늘린다

어르신은 문장 중간에 수 초씩 쉰다. 일반 설정(700ms)은 이 침묵을 발화 종료로 보고 앞부분만 넘긴다.

**발음이 아니라 여기서 생기는 실패가 있다.** 어르신 모드는 2000ms를 기다린다.

### 입력 시 — 어휘 힌트를 함께 넘긴다

그 사용자의 실제 거래 상대명과 계좌 별칭을 STT에 함께 넘겨 고유명사 인식률을 높인다. Gemini의 `custom_vocabulary`로 전달한다.

### 입력 후 — 깨진 텍스트를 교정하지 않고 후보와 대조한다

**이게 핵심이다.** 화면에 떠 있는 것(방금 읽어준 거래, 등록된 수취인, 가능한 의도)과 대조해 고른다.

1. 자모 단위로 분해해 편집거리 유사도를 잰다
2. 점수가 비슷한 후보가 둘 이상이면 LLM에 넘겨 선택하게 한다
3. 기준에 못 미치면 실행하지 않고 되묻거나 버튼으로 넘긴다

| 유사도 | 결정 |
|---|---|
| 0.80 이상, 2위와 0.10 이상 차이 | 채택 |
| 0.80 이상, 차이 0.10 미만 | LLM이 고름 |
| 0.60 ~ 0.80 | 되묻기 |
| 0.60 미만 | 후보 버튼으로 전환 |

**왜 이게 되나:** 사용자가 허공에 대고 명령하지 않기 때문이다. 알림을 눌러 들어오면 AI가 먼저 읽어주고, 사용자는 화면에 떠 있는 것에 대해 답한다. **후보가 유한하다는 조건 덕분에 인식 실패를 감당할 수 있다.**

### 실제 예시

`"그 정보통시인가 뭐시기"` — 의도 낱말도 상대명도 글자로는 안 맞는다.
자모로 재면 `정보통신`과 **0.91**. 잡아낸다.

## 5. 핵심 설계 ②: 모르는 것을 지어내지 않는다

읽어준 거래에 대해 더 물으면, 앱이 가진 정보로 답할 수 있는 것과 없는 것을 구분한다. 통장 적요만으로는 알 수 없는 항목이 있고, **여기서 그럴듯한 설명을 만들면 그대로 오안내가 된다.**

### 규칙 엔진 5개

| 규칙 | 조건 | 판정 |
|---|---|---|
| R1 | 등록된 수취인(사람) | **확인 가능** |
| R2 | 등록된 기관(한전·국민연금 등) | 부분 확인 |
| R3 | 적요가 기관 패턴과 매치 | 부분 확인 |
| R4 | 수수료 | **확인 불가** |
| R5 | 그 외 전부 | **확인 불가** |

**판정은 규칙 엔진이, 설명 문장만 LLM이 만든다.** 같은 입력에 같은 결과가 나와야 사후에 검증할 수 있기 때문이다. LLM에는 규칙 엔진이 만든 `facts`만 전달하고, 그 밖의 정보를 말하면 템플릿 문장으로 대체한다.

### 확장: 어떤 질문에도 막다른 길이 없다

거래 설명뿐 아니라 **은행 업무 질문 전체**에 같은 태도를 적용했다.

```
"적금 안내해줘"
→ "그건 제가 알려드리기 어려워요. 창구에서 여쭤볼 목록에 적어둘까요?"
```

인식이 깨진 것(`CLARIFY`, 후보 버튼)과 알아들었지만 답할 수 없는 것(창구로)을 **다르게 다룬다.** 못 알아들었을 때조차 선택지에 "그 밖의 것 창구에서 물어보기"가 있어서, 어떤 말을 하든 결국 창구 목록으로 갈 수 있다.

## 6. 핵심 설계 ③: AI에게 실행 권한을 주지 않는다

**저장소에 이체 실행 API가 아예 없다.** 잔액을 바꾸는 코드도 없다. 백엔드 컨트롤러 전수 확인했다.

"이체 요청"은 창구 요약서에 담기는 것뿐이고, 그 항목은 **확인 톤에서 "맞아요"를 받은 직후에만** 생성된다. 다른 경로가 없다.

```
확인하겠습니다. 받는 사람, 아들 김철수. 금액, 200,000원. 맞습니까?
   → "맞아요"  →  요약서에 담김
```

서버도 `confirmed_by_user: false`인 요청은 **400으로 거절한다.** 실제로 호출해서 확인했다.

### 확인 톤

되돌리기 어려운 행위 앞에서 말투가 바뀐다. 친근한 "-요"에서 또박또박한 "-습니다"로, TTS 속도도 0.85에서 0.8로 낮춘다. 화면도 배경과 테두리가 바뀌고 버튼이 [맞아요] [아니에요] 둘만 크게 남는다.

**화면 글자를 못 읽어도 말투 변화만으로 지금이 중요한 순간이라는 게 전달된다.**

---

## 7. 핵심 설계 ④: 창구로 넘긴다

요약서는 세 부분이다.

1. **창구에서 하려던 일** — 받는 사람, 금액, 계좌번호(마스킹)
2. **앱에서 확인되지 않아 여쭤볼 항목**
3. **준비물과 번호표**

계좌번호를 종이에 적어 가는 대신 앱에서 대화로 정리한다. 이 과정에서 받는 사람과 금액을 여러 번 되묻기 때문에 **창구 직원이 다시 확인하는 시간도 줄어든다.**

> 보통의 대화형 서비스는 AI가 답하지 못하면 거기서 끝나지만, 이 서비스에서는 그 지점이 창구로 이어지는 정상 경로다.

## 8. UI 결정: 왜 이모지를 안 썼나

물어볼 만한 질문이라 미리 정리해 둔다.

**이모지 찬성 논리는 분명하다.** 어르신들이 카카오톡에서 매일 보고, 배우지 않아도 안다.

**그런데 두 가지 문제가 있다.** 기기마다 모양이 달라 브랜드 색과 맞출 수 없고, 돈을 다루는 화면이 만화처럼 보이면 "이건 진짜 은행 기능"이라는 신호가 약해진다. 우리 서비스의 전제가 "어르신은 기계를 믿지 못한다"인데 여기서 신뢰를 깎으면 안 된다.

**더 중요한 건 아이콘이 아니라 글자다.**

> 햄버거 메뉴가 메뉴인 것도, 톱니가 설정인 것도 그걸 보고 자란 세대의 약속입니다. 어르신에게는 그냥 그림입니다. 그래서 아이콘을 장식으로만 쓰고 글자를 항상 함께 뒀습니다.

이건 "실패를 설계한다"는 우리 논지와 같은 태도다. **그림을 못 알아봐도 글자로 도달한다.**

### 그 밖의 화면 규칙

| 규칙 | 이유 |
|---|---|
| 버튼 최소 높이 72px, 글자 22px 이상 | 손이 떨려도 누를 수 있게 |
| 한 화면에 버튼 3개 이하 | 고를 것이 많으면 못 고른다 |
| 마이크는 스크롤 없이 보이는 위치 | 말하는 게 주 수단인데 안 보이면 안 된다 |
| 나가는 길은 항상 하나만 | 뒤로가기와 "그만"이 나란히 있으면 구분이 안 된다 |
| 음성으로 말한 것은 화면에도 크게 | 소리를 못 들어도 읽을 수 있게 |

## 9. 무엇을 만들었고 무엇을 안 만들었나

**솔직하게 말하는 것이 신뢰를 준다.** 범위를 먼저 밝히면 "왜 이건 없냐"는 질문이 안 나온다.

### 만든 것

| 영역 | 내용 |
|---|---|
| 프론트 | 진입 목업, 어르신 모드 홈·브리핑·대화·요약서, 직원 화면 |
| 백엔드 | 브리핑 선별, 분류 규칙 엔진, 창구 요약서, 직원 처리 API |
| AI 서버 | 음성 레이어 3겹, 대화 상태 머신, 어르신 모드 말투, TTS |

### 의도적으로 안 만든 것

| 안 만든 것 | 이유 |
|---|---|
| 로그인·본인인증 | 기존 앱이 이미 하는 일. `AuthProvider` 인터페이스로 경계만 정의했다 |
| 이체·조회·카드 화면 | 기존 KB스타뱅킹 기능. 누르면 화면이 직접 "범위 밖"이라고 말한다 |
| 음성 인식 모델 추가 학습 | 상용 STT 위에 레이어를 얹는 것이 이 프로젝트의 주장이다 |
| 실계좌·오픈뱅킹 연동 | 해커톤 범위 밖 |
| 영업점 번호표 시스템 실연동 | 목업이다. 실제로는 KB 모바일 번호표에 붙는다 |

> **실제 편입 시에는 `TransactionProvider`와 `AuthProvider` 두 인터페이스만 교체하면 됩니다.**

## 10. 예상 질문과 답

**Q. 왜 STT 모델을 학습시키지 않았나요?**
데이터도 시간도 없었지만, 그보다 이 주장이 더 강하다고 봤습니다. 모델을 바꾸지 않고 레이어만 얹어도 도달률이 오릅니다. 그러면 어떤 STT 엔진 위에도 얹을 수 있습니다.

**Q. 오인식으로 잘못 이체되면요?**
이체를 실행하지 않습니다. 저장소에 그 API가 없습니다. 요약서에 담기는 것뿐이고, 그것도 확인 톤에서 "맞아요"를 받아야 합니다. **확률로 막는 게 아니라 구조로 막습니다.**

**Q. LLM이 없는 말을 지어내면요?**
판정은 규칙 엔진이 합니다. LLM에는 규칙 엔진이 만든 사실만 전달하고, 그 밖의 숫자나 이름이 나오면 템플릿 문장으로 대체합니다. 같은 입력에 같은 결과가 나오므로 사후 검증이 됩니다.

**Q. 음성을 저장하나요?**
저장하지 않습니다. 메모리에서 처리하고 임시 파일은 지웁니다.

**Q. 대기시간이 줄어드나요?**
**대기시간은 안 줄어듭니다.** 앞에 선 손님 수는 그대로입니다. 줄어드는 건 **응대시간**입니다. 창구에 앉은 뒤 "무슨 일로 오셨어요"부터 시작하지 않고 확인부터 시작합니다. 많이 쓰이면 회전이 빨라져 대기시간도 줄겠지만 그건 이차 효과입니다.

**Q. 직원 화면은 아무나 보나요?**
고객이 6자리 코드를 보여줘야 열립니다. **코드를 보여주는 행위 자체가 동의입니다.** 직원이 먼저 검색하는 구조가 아닙니다.

**Q. 측정은 믿을 만한가요?**
자체 구성한 테스트셋 기준이라고 명시합니다. 같은 STT 엔진, 같은 입력을 레이어 적용 전후에 통과시켜 비교했습니다.

**Q. 어르신만 쓰나요?**
쉬운 안내에 대한 수요는 전 연령대에 있습니다. 고령층 전용으로 둘 이유가 없습니다.

## 11. 기대효과 (배점 30점, 가장 큰 항목)

### 사회적

배경의 세 가지 이유 중 앞의 둘(모른다, 잘못 누를까 봐)은 **대화 방식**으로, 세 번째(기계를 믿지 못한다)는 **창구 연계**로 다룹니다.

> 신뢰를 설득하는 대신 **믿지 않아도 쓸 수 있게** 만드는 접근입니다.

표준 발화가 어려운 사용자도 같은 기능을 쓸 수 있습니다.

### 경제적

용건이 정리된 상태로 방문하면 창구 **응대 시간**이 줄어듭니다. 다만 실제 효과는 영업점 상황에 따라 다르므로, 본 프로젝트에서는 요약서 사용 시 상담 시작까지 걸리는 시간을 자체 측정하는 선까지만 다룹니다.

은행 입장에서는 창구 혼잡 완화, 오안내 리스크 감소(판정 로그가 남습니다), 고령 고객 디지털 전환 지표가 있습니다.

### 기술적 확장

**대화(LLM)와 판정(규칙 엔진)을 나눈 구조**는 재현성과 사후 검증이 필요한 금융 서비스 전반에 적용할 수 있습니다.

**음성 대응 레이어는 특정 STT 엔진에 묶여 있지 않아** 기존 음성 서비스 위에도 얹을 수 있습니다.

### 3단계 로드맵

| 단계 | 내용 |
|---|---|
| 1 | KB스타뱅킹 어르신 모드 부가 기능 |
| 2 | 모바일 번호표 연동 + 영업점 태블릿 사전접수, KB 콜센터 전처리 |
| 3 | 전 연령 '쉬운 설명 모드', KB카드·KB손보·KB증권 알림으로 확장 |

## 12. 발표 순서 (7분 기준)

| # | 내용 | 시간 |
|---|---|---|
| 1 | 타이틀 + 트랙 + 한 줄 | 10초 |
| 2 | 문제: 창구에 가는 어르신, 세 가지 이유, 숫자 | 45초 |
| 3 | 기존 해법의 한계 비교표 | 30초 |
| 4 | 해결: 읽어준다 / 못 알아들어도 도달한다 / 창구로 넘긴다 | 30초 |
| 5 | **시연** | 2분 30초 |
| 6 | 구조 1장: LLM/규칙 분리, 레이어 3겹, 실행 권한 없음 | 40초 |
| 7 | 측정 결과: 레이어 전/후 | 30초 |
| 8 | 기대효과 + 3단계 로드맵 | 45초 |
| 9 | 마무리 | 10초 |

**시연에서 반드시 보여줄 것 네 가지**

1. 알림을 눌러 들어오면 **음성으로 읽어준다**
2. 확인 불가 거래에 **지어내지 않고 창구 목록에 담는다**
3. 뭉개진 발화도 **후보 대조로 잡아낸다** (또는 못 알아들으면 버튼으로 떨어진다)
4. 이체 요청이 **확인 톤을 거쳐 요약서로 가고, 직원 화면에 뜬다**
