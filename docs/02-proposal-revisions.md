# 기획서 수정·추가 문안

원본 기획서(『2026 KB IT's Your Life 해커톤』 기획서.docx)의 문체를 유지하며, 심사기준에 맞춰 바꾸거나 더할 문장을 **그대로 붙여 넣을 수 있게** 적었다. 결과보고서·PPT 에도 같은 문장을 쓴다.

---

## 1. 프로젝트 개요 (교체)

> **[디지털 금융약자 지원]** 어르신이 창구에서 하려던 일을 앱에서 미리 정리하고, 앱이 풀 수 없는 것은 그대로 창구 직원에게 넘기는 대화형 서비스.
> 입출금 알림을 눌러 들어오면 AI가 음성으로 내용을 읽어주고, 이어지는 질문을 대화로 받는다. 앱을 믿지 않는 사람도 쓸 수 있게 만드는 것이 목표다.

## 2. 사용 언어 (교체)

> ※ 프로토타입 구현 기준. 실제 편입 시에는 대상 뱅킹 앱의 스택을 따른다.
> Backend: Java 17, Spring Boot 3, MyBatis, MySQL 8.0 / Frontend: Vue 3 (모바일 웹)
> AI 서버: Python, FastAPI (상용 음성 인식·합성 API, 상용 LLM API — 벤더를 교체할 수 있는 어댑터 구조) / 협업: Git, GitHub Actions, Docker

## 3. 프로젝트 목표 — 구현 목표에 ④ 추가

> ④ 음성 대응 레이어를 거치지 않은 경로와 거친 경로에 같은 테스트셋을 통과시켜, 인식 정확도가 아니라 **의도 도달률·평균 시도 횟수·오실행 건수**로 비교 결과를 제시한다.

## 4. 프로젝트 목표 — "일정과 범위" (교체)

> □ 일정과 범위 (본선 2박 3일 기준)
> 1일차: 인터페이스 계약(API·대화 상태·분류 규칙·시연 데이터) 확정. 알림 브리핑과 음성 1턴까지 통합.
> 2일차: 음성 대응 레이어, 거래 확인 분류 규칙 엔진, 창구 요약서와 직원 화면. 시연 시나리오 완주, 테스트셋 측정.
> 3일차: 시연 안정화, 발표.
> 범위 밖: 음성 인식 모델 추가 학습, 실계좌·오픈뱅킹 연동, 영업점 번호표 시스템 실연동. 이체나 상품 가입처럼 돈이 움직이는 행위는 실행하지 않으며, AI에게 실행 권한을 주지 않는 것을 설계 조건으로 둔다.

## 5. 주요 특징 — ⑧ "안전·신뢰 설계" 절 추가 (⑦ 뒤에)

> ⑧ 안전·신뢰 설계
> · AI에게 실행 권한이 없다. 이체·가입처럼 돈이 움직이는 API는 이 시스템에 존재하지 않는다. 이체 요청은 창구 요약서에 담길 뿐이다.
> · 판정은 규칙 엔진이 한다. 확인 가능·부분 확인·확인 불가 분류와 실행 게이팅은 LLM이 아니라 규칙표로 결정되고, 어떤 규칙이 적용됐는지 응답에 남긴다. 같은 입력에는 같은 결과가 나온다.
> · LLM은 앱이 아는 사실만 받아 설명 문장을 만든다. 사실에 없는 숫자·이름이 응답에 나오면 정해진 문장으로 대체한다.
> · 음성 원본은 저장하지 않는다. 인식 결과와 판정 근거만 로그로 남긴다.
> · 요약서의 계좌번호는 마스킹한다. 창구 직원은 6자리 코드로 조회하고, 실제 계좌 확인은 창구 시스템에서 한다.

## 6. 주요 특징 — ⑨ "시연 시나리오" 절 추가

> ⑨ 시연 시나리오 (구현 목표와의 대응)
> 알림 탭 → 음성 브리핑 3건 [목표 ①] → "첫 번째 거 뭐야?" 확인 가능 설명 → "세 번째 그거 뭐야?" 확인 불가, 창구 목록에 담기 [목표 ③] → "아들이 뭐 보내라는데 이십만 원인가" 깨진 발화에서 수취인·금액 확정, 확인 톤 되묻기 [목표 ②] → 웅얼거림에 후보 버튼 제시 [목표 ②] → 창구 요약서·번호표 → 직원 화면에서 처리 → 앱에 완료 음성 [목표 ③] → 레이어 적용 전/후 측정 결과 [목표 ④]

## 7. 기대 효과 (전면 교체 — 배점 30점)

> □ 사회적
> 모바일뱅킹 이용자 중 60대 이상은 10.3%로, 은행 고객 중 비중(21.2%)의 절반이다. 이 격차가 잠재 사용자다. 배경의 세 가지 이유 중 앞의 둘(모른다, 잘못 누를까 봐)은 대화 방식으로, 세 번째(기계를 믿지 못한다)는 창구 연계로 다룬다. 신뢰를 설득하는 대신 믿지 않아도 쓸 수 있게 만드는 접근이다. 표준 발화가 어려운 사용자도 같은 기능을 쓸 수 있다.
>
> □ 경제적 (은행)
> 용건이 정리된 상태로 창구에 오면 직원은 확인 절차부터 시작할 수 있다. 본 프로젝트에서는 요약서 사용 시 상담 시작까지 걸리는 시간을 자체 측정해 제시한다. 실제 효과는 영업점 상황에 따라 다르다. 부수 효과로, 확인 불가 항목을 지어내지 않고 창구로 넘기므로 오안내 리스크가 줄고, 판정 로그가 남아 민원 시 사후 검증이 가능하다.
>
> □ 발전 가능성
> 1단계 — KB스타뱅킹 어르신 모드 부가 기능. 이 프로토타입의 경계면(거래내역 조회, 본인 인증)만 교체하면 된다.
> 2단계 — 영업점 연계. 영업점 태블릿 사전접수 도구, 번호표 시스템 연동, KB 콜센터 상담 전 용건 정리.
> 3단계 — 전 연령·계열사. 쉬운 안내에 대한 수요는 전 연령대에 있으므로 '쉬운 설명 모드'로 일반화하고, KB카드·KB손해보험·KB증권의 알림에 같은 브리핑·질문 구조를 붙인다.
>
> □ 확장성
> 음성 대응 레이어는 특정 STT 엔진에 묶여 있지 않아 기존 음성 서비스 위에 얹을 수 있고, 공공기관 민원·병원 예약처럼 '무엇을 물어야 할지 모르는 사용자'가 있는 다른 도메인에 그대로 적용된다. 대화(LLM)와 판정(규칙 엔진)을 분리한 구조는 재현성과 사후 검증이 필요한 규제 산업 전반에 쓸 수 있다.
>
> □ 측정 지표
> | 지표 | 정의 | 본 프로젝트에서 |
> |---|---|---|
> | 의도 도달률 | 발화가 깨져도 하려던 일(설명·요청·창구)에 도달한 비율 | 자체 테스트셋, 레이어 전/후 비교 |
> | 평균 시도 횟수 | 도달까지 걸린 턴 수(즉시 1, 되묻기 2, 버튼 3) | 〃 |
> | 오실행 건수 | 잘못된 상대·금액이 확정 단계로 들어간 건수 | 구조로 0 을 목표 |
> | 상담 시작까지 시간 | 요약서 제시 후 직원이 확인을 시작하기까지 | 리허설 자체 측정 |

## 8. 역할 분담 (교체)

> 안상우 : 백엔드(데이터). DB 설계·시연 데이터, 브리핑 선별 API, 거래 확인 분류 규칙 엔진, 알림·뮤트 API
> 고현준 : AI 서버·통합 리드. 음성 대응 레이어, 대화 상태 머신, 어르신 모드 응답 정책, 요약서 문장 생성, 인터페이스 계약 관리
> 이성우 : 프론트엔드(어르신 모드). 브리핑·대화·음성 UI, 녹음과 발화 종료 판정, 확인 톤 화면, 접근성
> 강두형 : 백엔드(요약서·인프라). 창구 요약서 API, 직원 API, 외부 인터페이스 추상화와 시연용 구현, Docker·CI
> 조태석 : 프론트엔드(목업·직원 화면)·시연·발표. 진입 목업, 직원용 요약서 화면, 성과 측정 도구, 시연 시나리오·발표 자료, 발표자
